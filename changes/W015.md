# W015: Learn from executable workflow gates

Status: trial.
Date: 2026-10-23.
Package version during inspection: `0.1.6`, unchanged by this inspection.

## Intent and scope

The user asked whether scripts can prevent skipped workflow steps when prompt instructions lose attention.
The user requested inspection of PPT Master and other large open-source projects.
This record compares official documentation and selected implementation paths.
It separates executable conditions, persistent state, and authority to approve.
The lessons remain proposals until the user approves their intended scope.

No external project was installed or executed.
No service, approval interface, experiment, or bypass test ran.
No framework or dependency was added to this toolkit.
The [W014 change](W014.md) records the separate human review policy trial and its later adoption.

A gate blocks an action until required conditions hold.
A receipt records a decision and its bound inputs.
Replay rebuilds saved workflow state from recorded events.
These mechanisms can reduce missed steps without proving scientific correctness.

## PPT Master: checks inside the consuming command

Default Generate uses two human planning confirmations.
Its confirmation server rejects invalid stage transitions and inconsistent template selections.
It writes receipts and compares hashes for selected resources and installed files.
The final planning gate can permit later production to continue automatically.
This differs from the requested review of every research intermediate output.
See the [Generate procedure](https://github.com/hugohe3/ppt-master/blob/523e5bd972f94c3cac8742fec0d54d43824a17bb/skills/ppt-master/workflows/generate-pptx.md#L128-L179).

Normal Default and Quick export require a final quality report before creating the PPTX.
The exporter rejects missing, unreadable, failed, non-final, or stale reports with a nonzero return.
Its fingerprint binds SVG filenames and bytes, rather than every project dependency.
The consuming command performs this gate even if an assistant forgets the earlier checker command.
See the [export gate](https://github.com/hugohe3/ppt-master/blob/523e5bd972f94c3cac8742fec0d54d43824a17bb/skills/ppt-master/scripts/svg_to_pptx/pptx_package/cli.py#L3123-L3149) and [report comparison](https://github.com/hugohe3/ppt-master/blob/523e5bd972f94c3cac8742fec0d54d43824a17bb/skills/ppt-master/scripts/svg_to_pptx/pptx_package/cli.py#L1248-L1344).

Local Host and Origin checks protect the confirmation server's web boundary.
They do not authenticate a human who approves a particular artifact.
The normal export gate does not inspect the human confirmation receipt.
Diagnostic sources, compatibility export, and the lower builder have different gate coverage.
These limits prevent a claim that every tool path enforces every human decision.
See the [confirmation handler](https://github.com/hugohe3/ppt-master/blob/523e5bd972f94c3cac8742fec0d54d43824a17bb/skills/ppt-master/scripts/confirm_ui/server.py#L2563-L2750) and [export boundary](https://github.com/hugohe3/ppt-master/blob/523e5bd972f94c3cac8742fec0d54d43824a17bb/skills/ppt-master/scripts/docs/svg-pipeline.md#L995).

## LangGraph: execution waits at a programmed boundary

An `interrupt()` call raises a runtime interruption when no resume value exists.
The configured checkpointer saves state, and a later `Command(resume=...)` supplies the response.
This blocks the programmed control flow instead of asking a model to remember to stop.
The response is application input, not proof that a human supplied it.
See the [implementation](https://github.com/langchain-ai/langgraph/blob/eb066bd31a2bf01fc0cd58256df4800a3695c233/libs/langgraph/langgraph/types.py#L1003-L1046) and [interrupt guide](https://docs.langchain.com/oss/python/langgraph/interrupts).

Resuming restarts the interrupted node from its beginning.
Operations before the interruption can therefore run again.
Separate consequential actions from the review node, or make repeated operations safe.
An in-memory checkpointer loses state after process restart.
Persistent storage and caller authorization remain deployment choices.
See the [replay cautions](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent) and [persistence guide](https://docs.langchain.com/oss/python/langgraph/persistence).

## Temporal: durable waits and validated updates

The SDK waits on a condition and resolves it only when its predicate becomes true.
An Update validator can reject a proposed state change before its handler runs.
The service records workflow history for later replay and recovery.
These mechanisms move waiting and continuation out of the model's conversation memory.
See the [wait implementation](https://github.com/temporalio/sdk-python/blob/a62ac75cf5306da2269af2b13cdf1d241334180a/temporalio/worker/_workflow_instance.py#L1966-L2015), [Update validation](https://github.com/temporalio/sdk-python/blob/a62ac75cf5306da2269af2b13cdf1d241334180a/temporalio/worker/_workflow_instance.py#L716-L778), and [event history](https://docs.temporal.io/encyclopedia/event-history).

The official approval sample accepts a programmatic Signal and a caller-supplied name.
That sample does not establish human identity or bind approval to an artifact digest.
Self-hosted authorization is separate: a configured Authorizer can reject calls, while the inspected empty configuration selects an allow-all implementation.
Completed history does not prevent repeated external effects from an in-flight Activity retry.
See the [sample client](https://github.com/temporalio/samples-python/blob/33f7dc29b2c68f01b65155b3b9a570dac67fabe0/message_passing/introduction/starter.py), [authorization selection](https://github.com/temporalio/temporal/blob/8a40a2663e304a79b07779ae08108648ccbc797d/common/authorization/authorizer.go#L64-L72), and [Activity guidance](https://docs.temporal.io/activity-definition).

## Apache Airflow: stored requests and authenticated responses

Airflow 3.3 uses a scheduler-managed `awaiting_input` state for human input.
Its database stores the request, response, assigned users, and continuation information.
The response API checks permissions and obtains the responder from its authenticated user dependency.
Assigned-user checks can further restrict who responds.
See the [3.3 tutorial](https://airflow.apache.org/docs/apache-airflow/3.3.0/tutorial/hitl.html) and [3.3.2 response API](https://github.com/apache/airflow/blob/aa19d2dbb9ed187ec01957a92848d9b005e9ba9d/airflow-core/src/airflow/api_fastapi/core_api/routes/public/hitl.py#L156-L274).

The inspected main scheduler can supply configured defaults when a request times out.
That response has no human responder, but it can still resume the task.
An approval default can therefore advance without a human answer.
Strict human review requires a policy that never converts silence or timeout into approval.
The newer request-version comparison is optional in the inspected main API and is not claimed here for release 3.3.2.
See the [timeout handling](https://github.com/apache/airflow/blob/99bdeabe3db437997d8d3c16353217fdaa350761/airflow-core/src/airflow/jobs/scheduler_job_runner.py#L3835-L3926) and [main response validation](https://github.com/apache/airflow/blob/99bdeabe3db437997d8d3c16353217fdaa350761/airflow-core/src/airflow/api_fastapi/core_api/routes/public/hitl.py#L196-L291).

## OpenHands SDK: approval at tool dispatch

The SDK can stop before executing pending tool actions and record `WAITING_FOR_CONFIRMATION`.
The configured confirmation policy decides whether that stop occurs.
The inspected release defaults to `NeverConfirm`.
A later `run()` call can act as approval of pending actions.
Direct `execute_tool()` calls explicitly bypass that confirmation policy.
See the [release default](https://github.com/OpenHands/software-agent-sdk/blob/60192ed54db73ac658ac1a07462916126c32d3a0/openhands-sdk/openhands/sdk/conversation/state.py#L119-L127) and [release invocation paths](https://github.com/OpenHands/software-agent-sdk/blob/60192ed54db73ac658ac1a07462916126c32d3a0/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L1959-L1967).

This makes the host's call boundary part of the approval design.
A model risk label, a host resume call, and an authenticated researcher decision are separate facts.
The SDK agent-server can check configured session keys, but that alone does not identify a particular human approval.
The inspected [security architecture page](https://docs.openhands.dev/sdk/arch/security) and source disagree on the default policy label.
The fixed release source is the basis for the default stated here.
See the [direct tool boundary](https://github.com/OpenHands/software-agent-sdk/blob/60192ed54db73ac658ac1a07462916126c32d3a0/openhands-sdk/openhands/sdk/conversation/impl/local_conversation.py#L3183-L3224), [server key check](https://github.com/OpenHands/software-agent-sdk/blob/dd0892c80fffb1e59bac77242adafbd8b1168649/openhands-agent-server/openhands/agent_server/dependencies.py#L21-L39), and [security guide](https://docs.openhands.dev/sdk/guides/security).

## Proposed minimum for this toolkit

The following design is an inference from these mechanisms, not an adopted implementation.
Its immediate purpose is to prevent accidental skipped steps under the normal execution path.
A separate authority boundary is needed before claiming that an assistant cannot approve its own work.
Adding a framework alone does not provide that boundary.

| Requirement | Proposed mechanism | Source lesson |
| --- | --- | --- |
| Stop use of an unapproved or changed output. | Bind each decision to a request ID, action, input versions, and output digests. Reject missing or stale decisions. | PPT Master and Airflow. |
| Make the next action inspect its own prerequisites. | Call a deterministic gate from the controlled dispatch or experiment entry, before the action starts. | PPT Master and OpenHands. |
| Recover after context loss. | Rebuild pending work from stored requests and decisions before dispatch. | LangGraph and Temporal. |
| Keep the human decision distinct. | Capture the decision through the harness or a separate authenticated reviewer interface. | Airflow authorization and Temporal's separate authorization layer. |
| Preserve explicit review defaults. | Treat rejection, expiry, revocation, silence, and timeout as reasons to stop dependent work. | Airflow defaults and OpenHands policy configuration. |
| Avoid duplicate work after recovery. | Bind repeated requests to stable IDs and inspect existing job evidence before retrying. | Temporal and LangGraph replay cautions. |

Start with a small review-state checker and a documented controlled entry point.
Keep ordinary research reasoning inside the existing stage procedures.
List every covered action and every bypass path before describing the gate as mandatory.
Do not give the producing agent permission to invent trusted approval events.
If the harness cannot separate those permissions, describe the result as a cooperative guard against omissions.

Consider a larger runtime only when distributed jobs, persistent scheduling, or many concurrent branches justify its operating cost.
LangGraph can supply resumable graph execution, but its approval caller still needs an authority design.
Temporal and Airflow add service infrastructure that this inspection does not justify installing now.
No comparative performance, research-quality gain, or reduction in skipped reviews was measured.

## Decision and next review

Decision: Retain these lessons as proposals.
The user authorized source inspection, not installation or adoption of an execution framework.
A script implementation requires a separate scope, fixed behavior cases, and a stated trust boundary.
Its tests must include changed versions, partial approval, revoked waivers, duplicate responses, missing decision sources, and unknown jobs.
The user separately approved W014 adoption after reviewing its candidate and evidence.
That approval does not adopt these runtime controls.

## Bounded implementation trial

Trial date: 2026-10-24.
Baseline package: `0.1.8`, after approved W016 adoption.
Isolated candidate package: `0.2.0`.
The user approved W016 adoption and continued the previously proposed sequence.
This authorizes preparation of the minimum gate candidate and its evidence.
Adoption still needs the user's review of that candidate.

The first implementation covers the existing bulk literature execution path.
It checks an explicit waiver before startup and before each external command.
The waiver must cover the exact effective configuration and every action in the uninterrupted pipeline.
Planning remains available without a waiver or file writes.
The candidate does not add a general task dispatcher or a workflow framework.

Use one candidate and a maximum of 60 minutes of assistant work.
Exclude time waiting for the user's response.
Use temporary directories, existing fake tools, offline tests, and an independent reviewer.
Do not use external accounts, paid services, real experiments, or network calls.
Keep existing task records, result records, state formats, and sealed examples unchanged.
Do not commit, push, or install a global skill copy.

Allowed code changes are `scripts/bulk_literature.py` and `tests/test_bulk_literature.py`.
Allow a new inert `templates/bulk-review.example.json`.
Allow the scripted bulk guide, human review guide, skill metadata, both README files, and bulk test documentation.
Allow this record, `tests/RESULTS.md`, and `tests/evidence/W015.json` for evidence.
Keep unrelated local work and earlier evidence intact.

Freeze cases before editing the implementation.
Compare the same cases with the saved baseline and candidate.
Test missing and stale records, partial scope, expiry, rejection, revocation, duplicate decisions, broken history, and missing sources.
Test revocation between commands and preservation of an unknown remote outcome.
Retain valid execution, safe recovery, query limits, integrity checks, and planning without effects.
An independent reviewer adds a separate case before inspecting the implementation.

The gate reads a supplied complete decision history and its source files.
It cannot authenticate a researcher, prove a source's meaning, or detect deliberately omitted history.
The producer must not invent actual approval records.

Direct external tools, altered scripts, and modified permission files remain bypass paths.
Direct `Pipeline.call(args)` use checks the log but does not bind arbitrary command arguments to the approved configuration.
The supported execution path uses the commands that `Pipeline.run()` creates.
A decision change cannot cancel a command that already started.
A denial after saving an operation's intent can leave a conservative pending record.

Version `0.2.0` marks an execution interface change.
Existing configuration and run files remain valid, but execution and recovery require a review log.
Old calls without that log stop before tools run.
The first slice requires a waiver because the uninterrupted pipeline cannot pause at each research output.
It does not mark generated answers as approved or permit their later scientific use.

The active repository remains at `0.1.8` during this trial.

## Observed candidate results

The fixed matrix contains 13 case groups and 23 concrete checks.
The final candidate met all 23 checks.
The baseline met the valid execution and safe recovery checks but lacks the new gate and plan binding fields.
These counts describe the new mechanical contract, not a model success rate.
Both versions used the saved baseline's fake external tools.

The independent reviewer froze two additional cases before inspecting the candidate.
One changes a decision source after the first command.
The other changes effective settings after constructing a pipeline.
The final candidate stopped before further calls in both cases.
The baseline continued both synthetic runs because it does not implement this gate.

The initial independent replay also passed on an earlier candidate revision.
A source symlink check moved before path resolution to handle loops on Python 3.9.
The reviewer repeated both frozen cases against the final code without changing their criteria.
The evidence preserves the first and final outputs separately.
An additional probe confirmed that arbitrary direct `Pipeline.call(args)` parameters remain outside configuration enforcement.
That exploratory probe is separate from the frozen case counts.

The baseline passed all 72 offline tests on Python 3.9.25 and 3.14.8.
The candidate passed all 90 offline tests on both versions.
This includes 23 retained bulk tests and 18 new gate tests.
The final package inspection covers completed documentation and evidence links.
No external research service or real approval event was used.

The [evidence record](../tests/evidence/W015.json) preserves the fixed criteria, actual command traces, independent assessment, test outputs, hashes, and exact candidate patch.
It also preserves the documented limits and the earlier independent replay.
Provider token use and cost were not measured.
This trial does not test long contexts, model compliance, live services, or a complete paper workflow.

## Candidate decision and recovery

Decision: The trial is complete, and the isolated `0.2.0` candidate awaits human adoption.
The result supports a cooperative gate on the normal bulk execution path.
It does not establish a trusted approval service or a gate for all research actions.
The user must review the new execution requirement before adoption.
The approved W016 package remains active at `0.1.8`.

If approved, compare intervening edits and apply only this reviewed candidate.
Keep existing run state, source files, decisions, and prior evidence unchanged.
If recovery needs an earlier package, reverse only this change and record that its mechanical gate no longer applies.
The next relevant real use must inspect source capture, waiver scope, and external tool behavior.
